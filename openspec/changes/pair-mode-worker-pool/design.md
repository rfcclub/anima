# Pair mode with a persistent worker conversation

## Architecture

The current clean base has `WorkerAdapter` and a one-session `low` microVM adapter, `WorkStore.reserveSession`, a workspace lock, stop records, and a review reconciler. It has no persistent worker pool. An earlier off-base pair-mode design isolates conversation state from HOME, places capacity allocation in `reserveSession`, and starts with a default-off config. Treat the prior local branch and qualification notes as candidate inputs. They do not establish features on this base or establish a live deployment. Reconcile or reuse its config slice before opening duplicate implementation work.

**Main and review.** Add `work.pairMode` (default false) under the existing configuration. Keep the host as authority for the one active assignment, keyed by work/session/generation. A worker returns one bounded typed report through the adapter seam, normalized to done, unverified, error, question or stopped short. Accept only the active assignment’s report. Main uses the existing `checkpointed`, `in-review`, and `revising` transitions and independent review requirements. Worker output is a claim. An approval remains a review decision. A revision on the same backend receives fresh review feedback and a validated conversation reference.

**Slot lifecycle.** Store a global capacity pool with a proposed initial size of four slots and an allowed range of one to six; this is a pair-pool setting, separate from the author-lane trial. In one SQLite transaction, acquire a slot together with the work reservation and generation/session charge. A full pool returns a release outcome with no reservation state, budget or generation change. Preserve the existing workspace lock and require a release-capable queue for pair mode. Live jobs can wait with backoff until their expiration; a distinct reconciliation step records an expired assignment with a visible blocked reason and uses the existing operator recovery boundary. A slot becomes free only after positive cessation evidence tied to the claimed session and generation. Stale or crashed leases quarantine their slot; retries either prove cessation or leave it quarantined. Shrinking configured capacity cannot evict leased or quarantined slots. Free capacity is not proof of work completion.

**Conversation lifetime and environment.** Keep only a validated work-scoped conversation snapshot under host-owned storage. Each physical low process starts in a fresh VM/HOME with a fresh gateway capability, generated config and readiness marker. Copy only supported history into the fresh directory before start. Snapshot only after cessation under the host generation fence and before normal cleanup. Missing or invalid history starts a new conversation with an explicit status and the current task; a changed backend always starts fresh. Do not deploy a long-running worker server without a separate qualification decision. Validate one-shot resume in the pinned VM build, strict filesystem/environment allowlist, and the five exit mappings before activation. Provider/model changes are applied at a session boundary with the configured ordered fallback. Only positively classified quota/rate-limit cases trigger automatic fallback; ambiguous errors remain ordinary failures. Same-backend resume across a model switch requires qualified support; a new conversation is announced if required.

**Watchdog and steering.** Use the observable progress boundary of the VM runner rather than a final buffered output read. Once a bounded silence threshold elapses, Main can steer or abort. Steering cancels through the existing lease and cessation path and queues a bounded revision for the next session; it cannot authorize a new writer. Never treat a slow or unproven stop as safe to resume.

**Evidence and protected paths.** Keep host-owned checkpoint, commit and check evidence. The host verifies the exact branch ancestry and changes against a pinned starting commit under the existing protected-path and publication rules; host-configured checks run without worker credentials. The worker cannot publish or approve. A worker-created commit remains subject to the existing policy until an explicitly reviewed slice adds a safe exact-object verification path; ordinary host-owned completion is sufficient for the first pair pilot.

## Test strategy

Use a temporary real WorkStore for contention, budget, stale generation, restart and quarantine. Use fake worker processes for exit mappings, per-session HOME and readiness/credential isolation, ordered fallback, progress timeout and cancellation. Use controlled real Git repositories for branch and protected-path evidence. Run legacy work tests with pair mode disabled. A separately authorized real VM qualification measures the pinned backend with fake gateway input before activation. The #375 pilot verifies the S1/S2 boundaries with evidence attached to an exact candidate commit.
